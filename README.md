# Puck
*"that shrewd and knavish sprite"*

## What is it?
Puck is an implementation of a programmable space that takes in visual input from a generic webcam and uses that to generate different projections. It does this by recognizing physical pieces of paper which are placed on a table in front of the camera. These papers are associated with user defined code which generate a response in the system, typically using projections. When the programs are moved about, the system registers their physical movement and reacts accordingly, allowing dynamic spatial input and output using light and paper.

## How do I use it?

### Dependancies

You will need
- Python: This project depends on Python 3.14 or higher
- UV: Please install UV as it is our package manager for this project.

Fork your own copy of the repo. Then upon opening it, call `uv sync` to install all the required dependancies.
For more on uv look at: https://docs.astral.sh/uv/

### Running Puck

To run Puck call `uv run puck`. This will start the detection system.

It will first establish a homoography matrix to align the detected space with the projection space. This involves displaying a chessboard onto your flat surface briefly, so please clear your work space lest it confuse the system. If the chessboard cannot find even a tilted flat surface it will struggle to create a homography matrix. 

Then it will look for papers with AprilTags which it will use to call the program associated with each paper and run that program.

This will continue until you end the Puck system on your laptop or press 'q' on an input keyboard.

## Puck Files in this Repo

## Main

This handles the running of all the programs as well as the graphics creation for the system. Because graphics are generated by Tkinter all of the graphics calls must occur in the main thread (a constraint of Tkinter). The average user should not need to access the main.py file.

## Geometry Module
This module handles all of the geometric commands Puck uses. It will be called in main but likely will not be necessary to explore in individual applications unless to debug interactions with main.py. It does establish the classes `Point` and `Polygon` which hold an (x,y) point and a list of Points which make up a shape, respectively.

To read more about this module please read the docstring at the beginning of the Geometry module.

## Actor System
Inspired by Erlang's actor system, we have implemented an Actor class which extends the Python thread class. It has a generalized Actor class as well as a more specific DrawingActor subsclass which directly interacts with graphics generation. Both, as extensions of threads, need a target function (commonly called a process) which they will run upon calling `[actor].start()`. This allows each program to run in its own thread and communicate with each other and the main thread with message passing. 

To read more about this please read the docstring at the beginning of the Actor module.

## Programs

Please use the program folder to store your programs for the system in. As the actor system is still in progress programs are not abstracted enough to just be a call to:
`print("Hello World")`
Instead programs are very much message handling instances which determine how different messages can be handled. Samples of this will be put into the programs folder for reference, `test.py` is an example that can be used right now.

Whatever programs you do create must be added to the `program_lookup.json` in the data folder where its index in the list will be used as the encoding for the apriltags.
